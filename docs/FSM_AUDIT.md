# Auditoría de máquinas de estado implícitas

**Fase:** 0 — auditoría, sin cambios de runtime
**Fecha de inspección:** 11 de noviembre de 2026
**Rama base inspeccionada:** master
**Resultado:** inventario contrastado con el código actual; las rutas citadas son las reales.

## Criterio de clasificación

- **MIGRAR:** el estado tiene guards, efectos laterales relevantes, varios escritores o coordina más de un sistema. Se indica la fase y si corresponde una FSM ECS o una tabla/helper sin ECS.
- **HELPER:** el estado ya tiene un propietario central y una API clara. Conviene proteger las transiciones con transition(), pero no convertirlo en una FSM por entidad.
- **DEJAR:** el campo es configuración, dato derivado, metadato, no tiene escritores reales o una migración introduciría una máquina sin comportamiento que modelar.

Los escritores indicados son los escritores de runtime localizados; inicializadores y mutaciones explícitas de tests se distinguen de ellos. Las asignaciones se contrastaron con la lectura de los sistemas pertinentes.

## Consecuencias para las fases siguientes

1. **Fase 1:** crear transition(from, to, table) en core y RunPhase en gameplay-kit. Candidatos confirmados: Asteroids, Geometry Wars, Echo Runner, Vertical Shmup y la parte terminal de Arkanoid. Racing ya dispone de phase=finished; no añadir otro estado redundante. Mantener los flags/getters que formen parte de contratos externos.
2. **Fase 2:** en Space Invaders, consolidar ready/intermission/continue como estados mutuamente excluyentes, pero conservar el contrato que Schedule lee hoy (PLAYING, WAVE_TRANSITION, MUTATOR_DRAFT) y el significado de game over. La auditoría no encuentra productor runtime para WAVE_TRANSITION ni GAME_OVER en el discriminador existente; esto debe resolverse explícitamente, no inferirse.
3. **Fase 3:** la FSM genérica SpawnDirector debe conservar la secuencia completa; Tower Defense solo consume idle/spawning. El status de SpawnDirector tiene que tener un único punto de transición sin desplazar los guards de scheduler ni el conteo de entidades vivas.
4. **Fase 4:** Capturable es el piloto idóneo por su API y tres resultados observables. Conservar capture:trapped, capture:popped y capture:escaped y sus payloads actuales; añadir el nuevo evento tipado (entityId, from, to) como canal adicional, no como sustitución.
5. **Fase 5:** migrar FSM por entidad con timers como datos deterministas. En Galaxian el límite de dives y la selección de escorts siguen fuera de la FSM. En Kamikaze, la entrada a warning requiere confirmar un productor real; el spawner observado crea telegraphing directamente.
6. **Fase 6:** definir la tabla del Orchestrator y validar la coherencia con ArcadeKernel.VALID_TRANSITIONS (packages/core/src/runtime/ArcadeKernel.ts:43-52). Las rutas failed/aborted/resolving se proyectan a más de un estado del kernel según resultado; no son una correspondencia 1:1. Los estados globales GameLifecycle, SceneManager, Tower Defense, Racing, HeadToHead y Centipede justifican tablas/helpers no-ECS, no StateMachineRegistry.

## Límites de esta fase

Esta fase solo añade este documento. No se cambian componentes, sistemas, registros de eventos, barrels, colores, configuración ni snapshots. No se ha ejecutado pnpm run ci localmente desde el conector GitHub: la verificación automatizada de la rama debe consultarse en los checks del PR; no se debe marcar la fase como validada hasta confirmar esos checks. No se modifica la baseline de duplicación porque no se ha ejecutado ni se ha demostrado una reducción.
